# 编辑选题供稿系统方案

## 1. 目标

每天固定在 `07:00`、`10:00`、`13:00`、`16:00` 生成一份供编辑选题用的热点清单。

理想输出形态：

```text
2026-07-09 10:00 选题池

AI / 科技
1. 标题 - 链接
2. 标题 - 链接
...
20. 标题 - 链接

财经 / 市场
1. 标题 - 链接
...
20. 标题 - 链接

消费 / 公司
...
```

核心要求：

- 每个赛道给 `20` 条。
- 一条标题对应一个链接。
- 尽量是当前时间段的新内容，而不是早上已经看过、下午还排在最前的旧内容。
- 同一件事不要重复出现。
- 已经发给群里的内容，后续批次默认不再重复发。
- `/hotlists/` 可以继续作为来源看板，但不再承担最终编辑供稿排序。

## 2. 当前情况

### 2.1 来源热榜页面

当前线上来源热榜：

- `https://newshot-5jq.pages.dev/hotlists/`
- 本地预览类似：`http://127.0.0.1:8788/?t=1781440194`

它现在主要是一个“来源视角”的看板：

- 微博、今日头条、百度、抖音、知乎、Bilibili、雪球等来源来自 TrendRadar 抓取。
- 金十数据已经支持前端手动实时刷新。
- 财联社电报时间流目前还是静态页，不能前端实时刷新。
- 点击微博、抖音、今日头条等 tab，只是切换当前页面已经生成好的内容，不会重新抓取源站。
- 浏览器刷新也只是重新请求已经部署好的页面，不会触发采集。

### 2.2 更新频率

当前 GitHub Actions 配置是：

```yaml
schedule:
  - cron: "17 */2 * * *"
```

这意味着大约每 2 小时自动跑一次。它会：

```text
TrendRadar 抓热榜
→ 生成行情
→ 生成财联社电报页
→ 生成 curated / hotlists 页面
→ 生成日报
→ 部署到 Cloudflare Pages
```

完整流程经常需要 15 分钟左右。因此，其他热榜并不是实时的。

### 2.3 金十数据

金十数据现在不完全依赖静态页。已经加了：

```text
/api/jin10/flash?refresh=1
```

前端按钮点击后，Cloudflare Pages Worker 会在服务端实时抓金十，并按当前规则过滤：

```text
important=1 或 爆 / 沸 / 热 / 火
```

然后按时间倒序替换金十模块。

### 2.4 公众号分类网站

当前还有一个本地公众号分类网站：

```text
http://127.0.0.1:8001/
```

它的作用更接近“人工分类 / 赛道归类”。问题是：如果排序只看已有热度或分类结果，没有时间窗口和已发送历史，就会出现较早新闻排在靠前位置的情况。

### 2.5 当前系统的主要问题

1. `/hotlists/` 是来源视角，不是编辑供稿视角。
2. 大部分来源更新依赖 2 小时一次的完整部署。
3. tab 切换不等于刷新。
4. 排序没有严格按供稿时间窗口控制。
5. 缺少“已发历史”，旧内容会反复出现。
6. 分类网站可以辅助赛道判断，但不应该直接决定最终排序。

## 3. 先召回还是先聚类

结论：**先召回，再聚类，再排序。**

更准确地说，是：

```text
来源采集
→ 标准化
→ 大召回
→ 初步分类
→ 去重 / 聚类
→ 聚类级排序
→ 每个赛道取 20 条
→ 记录已发送历史
```

### 3.1 为什么不是先聚类

聚类需要候选数据。没有召回，就没有候选池可以聚类。

如果一上来对所有历史数据聚类，会有几个问题：

- 数据量大，成本高。
- 很多旧新闻、低质量内容也参与聚类。
- 容易让旧的大事件持续占据靠前位置。
- 不符合“7 点、10 点、13 点、16 点这几个批次”的编辑节奏。

### 3.2 召回不是最终入选

这里的“召回”不是说直接选中，而是先把“可能有用的候选内容”捞出来。

召回应该宽一点，排序再严格一点。

可以理解为：

```text
召回：宁可多捞一点，别漏掉重要内容。
聚类：把同一件事合并。
排序：决定哪些真正给编辑看。
```

### 3.3 推荐使用两层召回

第一层是来源召回：

```text
从各来源抓取原始热榜 / 快讯 / 电报
```

第二层是编辑候选召回：

```text
在指定时间窗口内，保留可能适合选题的内容
```

完整顺序：

```text
源站内容
→ 来源召回
→ 标准化 item
→ 编辑候选召回
→ 聚类为 event / topic
→ 赛道分类
→ 排序
→ 输出
```

目标：

```text

```

## 5. 标准化层

每个来源拿到的数据格式不同，必须先统一成同一种 item。

推荐字段：

```text
id                  内部唯一 id
source_id           来源 id，例如 weibo / toutiao / jin10
source_name         来源名称
title               标题
url                 链接
raw_url             原始链接，如果和展示链接不同
summary             摘要，可为空
rank                来源内排名，可为空
hot_value           热度值，可为空
source_labels       来源标签，例如 important、火、热
official_category   来源官方分类，例如金十的 A股、美股、地缘局势
first_seen_at       第一次看到时间
last_seen_at        最近一次看到时间
published_at        内容发布时间，如果源站提供
fetched_at          抓取时间
content_hash        标题归一化后的 hash
raw_payload         原始数据 JSON
```

这一步只做“格式统一”，不做最终取舍。

## 6. 召回层

召回的目标是建立一个候选池。

### 6.1 时间窗口召回

每个批次应该有自己的主时间窗口。

| 批次 | 主窗口 | 兜底窗口 | 说明 |
| --- | --- | --- | --- |
| 07:00 | 前一晚 20:00 到当天 07:00 | 过去 12 小时 | 覆盖夜间和早间突发 |
| 10:00 | 07:00 到 10:00 | 过去 6 小时 | 早盘、上午热点 |
| 13:00 | 10:00 到 13:00 | 过去 6 小时 | 午间更新 |
| 16:00 | 13:00 到 16:00 | 过去 6 小时 | 下午收盘前后 |

主窗口优先。主窗口不够 20 条时，再从兜底窗口补。

### 6.2 来源召回规则

不同来源的召回规则不同。

#### 金十数据

当前规则可以保留：

```text
important=1 或 爆 / 沸 / 热 / 火
```

排序只按时间，不按 important 或 hot 排序。important 和 hot 只作为召回条件。

#### 财联社电报

建议后续做成类似金十：

```text
按时间流抓取
保留最近窗口内内容
可按关键词或财联社标签辅助召回
```

财联社电报不应该和日报、热点脉络平行，而应该作为来源热榜或快讯源进入候选池。

#### 社交热榜

微博、抖音、今日头条、百度等可以保留：

```text
来源排名前 N
或者热度值超过阈值
或者短时间内排名上升
```

建议每个来源每次保留：

```text
Top 50 到 Top 100
```

不要过早只取 Top 10，否则很多垂直赛道会被娱乐和社会热点挤掉。

#### 行业源 / 公众号源

可以按赛道关键词召回：

```text
AI、模型、芯片、自动驾驶、低空经济、消费、跨境、电商、医药、地产、政策、金融市场等
```

这类召回可以宽一点，因为后面会聚类和排序。

### 6.3 召回不要解决排序问题

召回只回答：

```text
这条内容有没有资格进入候选池？
```

不要让召回直接决定：

```text
这条内容是不是最终第 1 名？
```

最终第几名应该由排序层决定。

## 7. 聚类 / 去重层

聚类的目标是把同一件事合并成一个事件。

例如：

```text
微博：某公司发布新车
今日头条：某公司新车售价公布
金十：某公司新车订单突破 X
```

这些可能都属于同一事件，最终给编辑时不应该重复出现三次。

### 7.1 聚类输入

聚类输入应该是召回后的候选池，而不是全量历史库。

原因：

- 候选池更干净。
- 更符合当前批次时间窗口。
- 计算更轻。
- 避免旧新闻持续干扰。

### 7.2 聚类方法

可以先用规则，不必一开始就上复杂模型。

推荐组合：

1. 标题归一化
   - 去掉标点。
   - 去掉“最新”“刚刚”“热搜”等无意义词。
   - 中英文大小写统一。
   - 去掉来源后缀。

2. URL 去重
   - 同一 URL 直接认为同一条。
   - 跳转链接需要尽量取最终链接。

3. 标题相似度
   - 归一化标题完全包含。
   - 文本相似度超过阈值。
   - 建议初始阈值：`0.78` 到 `0.85`。

4. 实体 + 动作
   - 同一公司 / 人物 / 地点。
   - 同一动作，例如发布、涨停、被调查、融资、事故、回应。

5. 时间接近
   - 同一事件通常在几小时内集中出现。
   - 时间差太远时，即使标题相似，也要谨慎合并。

### 7.3 聚类输出

聚类后形成 cluster。

推荐字段：

```text
cluster_id
title
representative_url
items
sources
source_count
first_seen_at
last_seen_at
primary_track
secondary_tracks
score
sent_status
```

### 7.4 代表标题和链接怎么选

每个 cluster 最终只能输出一条标题和一个链接。

代表内容选择规则：

1. 优先选有明确原文链接的。
2. 优先选标题清楚、信息密度高的。
3. 优先选权威来源。
4. 如果是快讯，优先选最新一条。
5. 如果是社交热榜，避免只给搜索页，除非没有更好链接。

## 8. 分类 / 赛道层

### 8.1 分类可以在聚类前后各做一次

这里容易混乱。推荐做法是：

```text
item 级初步分类
→ cluster 聚类
→ cluster 级最终分类
```

item 级分类用于帮助召回和聚类。

cluster 级分类用于最终输出。

### 8.2 为什么要 cluster 级最终分类

同一事件可能来自多个来源，每个来源的分类都不完全可靠。

比如金十可能把一条地缘冲突新闻标成美股，因为它影响美股市场。但编辑供稿时，这条更应该进“国际 / 地缘 / 财经市场”中的某个主赛道。

所以最终分类应该基于整个 cluster 判断，而不是只看某一条来源标签。

### 8.3 赛道建议

具体赛道可以按公众号业务来定。一个可用的初始版本：

```text
AI / 科技
财经 / 市场
公司 / 商业
消费 / 品牌
汽车 / 出行
地产 / 城市
医药 / 健康
政策 / 宏观
国际 / 地缘
社会 / 民生
文娱 / 体育
```

如果公众号分类已经有固定类目，应以公众号类目为准。

### 8.4 分类网站的角色

`http://127.0.0.1:8001/` 建议作为：

```text
人工校正分类
人工置顶 / 拉黑
维护关键词和赛道规则
查看待确认候选
```

不建议让它直接决定最终排序。

最终排序应该由供稿系统根据时间窗口、热度、来源权重、去重历史统一计算。

## 9. 排序层

排序目标是：

```text
每个赛道选出当前批次最值得编辑看的 20 条
```

### 9.1 为什么旧新闻会靠前

旧新闻靠前通常有几个原因：

1. 旧新闻在多个来源出现，累计分高。
2. 旧新闻曾经排名很高。
3. 当前排序没有强时间衰减。
4. 没有记录“上一批已经发过”。
5. 分类之后没有按批次窗口重新排序。

### 9.2 推荐排序公式

可以先用可解释的规则分数。

```text
final_score =
  freshness_score
  + heat_score
  + source_score
  + cross_source_score
  + track_match_score
  + novelty_score
  - stale_penalty
  - duplicate_penalty
  - sent_penalty
```

各项含义：

| 分数 | 含义 |
| --- | --- |
| freshness_score | 越新越高 |
| heat_score | 来源排名、热度、hot 标签 |
| source_score | 来源权重 |
| cross_source_score | 多来源同时出现加分 |
| track_match_score | 和赛道越匹配越高 |
| novelty_score | 新出现事件加分 |
| stale_penalty | 超过当前窗口扣分 |
| duplicate_penalty | 与已有 cluster 重复扣分 |
| sent_penalty | 已经发过的内容扣分或直接过滤 |

### 9.3 时间衰减

强烈建议加入时间衰减。

一个简单版本：

```text
0 到 1 小时：满分
1 到 3 小时：轻微衰减
3 到 6 小时：明显衰减
6 小时以上：只作为补位
12 小时以上：默认不进普通批次
```

对不同批次可以不同：

```text
07:00 可以接受夜间 12 小时窗口
10:00、13:00、16:00 应该更强调最近 3 小时
```

### 9.4 已发送历史

必须有 sent history。

推荐维护一张表：

```text
sent_id
cluster_id
title_hash
representative_url
track
batch_time
sent_at
```

每次生成前检查：

```text
同一 cluster 今天发过：不再发
相似标题今天发过：不再发
同一 URL 今天发过：不再发
```

如果某事件有重大新进展，可以允许再次出现，但标题中必须有新的增量信息。

### 9.5 每赛道 20 条怎么取

推荐流程：

```text
1. 每个 cluster 有 primary_track。
2. 按 primary_track 分桶。
3. 每个桶内按 final_score 排序。
4. 每个赛道取前 20。
5. 如果不足 20，从兜底窗口补。
6. 仍不足 20，则保留实际数量，不要硬塞低质量旧内容。
```

## 10. 批次时间设计

### 10.1 供稿批次

| 北京时间 | 主要用途 |
| --- | --- |
| 07:00 | 早间选题，覆盖夜间、海外、早盘前 |
| 10:00 | 上午更新，覆盖开盘后、社交热榜启动 |
| 13:00 | 午间更新，覆盖上午发酵和午盘 |
| 16:00 | 下午更新，覆盖收盘、全天后续 |

### 10.2 GitHub Actions cron

GitHub Actions 的 cron 使用 UTC。

北京时间转换：

| 北京时间 | UTC |
| --- | --- |
| 07:00 | 前一天 23:00 |
| 10:00 | 当天 02:00 |
| 13:00 | 当天 05:00 |
| 16:00 | 当天 08:00 |

可以配置：

```yaml
schedule:
  - cron: "0 23,2,5,8 * * *"
```

脚本内部再按 `Asia/Shanghai` 判断当前批次名称。

## 12. 工作流拆分建议

### 12.1 当前 workflow 的问题

现在一个 workflow 同时做太多事：

```text
抓热榜
生成行情
生成电报
生成来源热榜
生成日报
部署
```

这导致：

- 更新慢。
- 不能高频跑。
- 任一步慢都会拖住热榜刷新。
- 不适合编辑供稿这种固定时间任务。

### 12.2 推荐拆成两个 workflow

#### workflow 1：热榜快速更新

用途：

```text
更新来源池和 /hotlists/
```

频率：

```text
每 15 到 30 分钟
```

只做：

```text
TrendRadar 抓取
金十 / 财联社快讯抓取
生成 hotlists
生成 normalized pool
部署
```

不做：

```text
日报
热点脉络
长周期分析
```

#### workflow 2：编辑供稿批次

用途：

```text
每天 07:00、10:00、13:00、16:00 生成每赛道 20 条
```

只做：

```text
读取最近候选池
必要时补抓实时源
召回
聚类
分类
排序
生成 briefing
写 sent history
部署或推送群
```

### 12.3 长内容日报暂时停更

长内容日报暂时停更，不再参与常规部署生成。

当前重点先放在：

```text
来源热榜
实时快讯
编辑供稿 briefing
```

等编辑供稿流程稳定后，再决定是否恢复长内容日报，或者改成每天低频生成。

## 13. 和群推送的关系

第一阶段不必直接自动发群。

可以先生成：

```text
/briefing/latest.md
```

你手动复制到群里。

稳定后再接：

- 飞书机器人
- 企业微信机器人
- 钉钉机器人
- 邮件
- 本地脚本复制到剪贴板

自动发群前一定要先有 sent history，否则容易重复发。

## 14. 分阶段改造计划

### 阶段 1：先做可用的编辑供稿页

目标：

```text
生成 /briefing/latest.md 和 /briefing/latest.html
```

数据来源：

- 现有 TrendRadar output
- 金十实时接口
- 财联社电报静态结果
- 公众号分类结果，如果能导出

功能：

- 按批次时间窗口召回。
- 简单聚类去重。
- 按赛道分类。
- 每赛道输出 20 条。
- 记录已输出历史。

### 阶段 2：拆热榜快速 workflow

目标：

```text
把 /hotlists/ 更新频率从 2 小时缩短到 15 到 30 分钟
```

做法：

- 新建一个 hotlists-only workflow。
- 不跑 daily_digest。
- 不跑长周期日报。
- 只部署热榜和候选池。

### 阶段 3：财联社电报实时化

目标：

```text
财联社电报像金十一样可以前端刷新
```

做法：

- 增加 `/api/cls/telegraph`。
- 前端“刷新当前来源”支持财联社电报。
- 编辑供稿任务也可以在批次生成前实时补抓。

### 阶段 4：公众号分类系统接入

目标：

```text
分类网站成为赛道标注和人工校正后台
```

做法：

- 供稿系统把候选内容输出给分类网站。
- 分类网站写回 track override。
- 供稿系统读取 override 后再排序。

### 阶段 5：自动群推送

目标：

```text
每天 07:00、10:00、13:00、16:00 自动推送
```

前提：

- 输出质量稳定。
- sent history 稳定。
- 分类准确率可接受。
- 有人工兜底页面。

## 15. 最小可行版本

如果想尽快做出来，不要一开始做太复杂。

最小版本可以这样：

```text
输入：
  现有 output 热榜数据
  金十实时数据
  财联社电报数据

处理：
  过去 3 到 6 小时召回
  标题相似去重
  规则分类到赛道
  freshness + source_rank + source_weight 排序
  已发过的不再出现

输出：
  output/briefing/latest.md
  output/briefing/latest.html
```

这样就能先解决最痛的问题：

- 不再靠 `/hotlists/` 手动翻。
- 不再让早新闻长期排第一。
- 每个赛道都有固定格式。
- 可以直接复制到群里。

## 16. 推荐结论

你的目标不是“更好看的热榜”，而是“编辑供稿流水线”。

因此推荐路线是：

```text
来源抓取
→ 大召回
→ 聚类去重
→ 赛道分类
→ 时间窗口排序
→ 每赛道 20 条
→ 写入已发历史
→ 生成 Markdown
```

先召回，再聚类。

但召回要宽，排序要严。

`/hotlists/` 继续当来源看板；真正给编辑群用的，应该是新的 `/briefing/` 供稿页。
