# 编辑选题供稿系统方案

更新时间：2026-07-10

本文是新开对话时最重要的项目上下文：它记录了本轮讨论后确定的 NEWSHOT 编辑供稿方向。`/hotlists/` 继续作为来源看板；最终给群里复制粘贴的产物应该是 `/briefing/latest.md`。

## 1. 目标

每天固定在 `07:00`、`10:00`、`13:00`、`16:00` 生成一份供编辑选题用的热点清单。

最终输出就是一份 Markdown 文本，直接复制到群里即可。

推荐输出形态：

```markdown
# 2026-07-09 10:00 编辑选题池

窗口：07:00-10:00；每赛道最多 20 条；已过滤本日已发送进展。

## AI / 科技

1. [某公司发布新一代大模型，支持多模态实时交互](https://example.com/a)
2. [英伟达新芯片供应链消息发酵，相关公司回应](https://example.com/b)
...
20. [标题](https://example.com)

## 财经 / 市场

1. [A股三大指数午后回落，半导体板块逆势走强](https://example.com/c)
...
20. [标题](https://example.com)

## 消费 / 公司

1. [某茶饮品牌回应加盟商调整，门店扩张节奏放缓](https://example.com/d)
...
```

核心要求：

- 每个赛道给 `20` 条。
- 每条只保留 `标题 + 链接`，不输出复杂解释、打分和调试字段。
- 群里优先使用 Markdown 链接格式：`1. [标题](链接)`。
- 如果群工具不支持 Markdown，可以降级为：`1. 标题 - 链接`。
- 尽量是当前时间段的新内容，而不是早上已经看过、下午还排在最前的旧内容。
- 同一事实不要重复出现。
- 同一事件有新进展时，可以再次出现，但必须输出新的 progress。
- 已经发给群里的 progress，后续批次默认不再重复发。
- `/hotlists/` 可以继续作为来源看板，但不再承担最终编辑供稿排序。

## 2. 当前情况

### 2.1 来源热榜页面

当前线上来源热榜：

- `https://newshot-5jq.pages.dev/hotlists/`
- 本地预览类似：`http://127.0.0.1:8788/?t=1781440194`

它现在主要是一个“来源视角”的看板：

- 微博、今日头条、百度、抖音、知乎、Bilibili、雪球等来源来自 TrendRadar 抓取。
- 金十数据已经支持前端手动实时刷新。
- 财联社电报时间流目前还是静态页，不能前端实时刷新。
- 点击微博、抖音、今日头条等 tab，只是切换当前页面已经生成好的内容，不会重新抓取源站。
- 浏览器刷新也只是重新请求已经部署好的页面，不会触发采集。

### 2.2 更新频率

当前 GitHub Actions 配置是：

```yaml
schedule:
  - cron: "17 */2 * * *"
```

这意味着大约每 2 小时自动跑一次。它会：

```text
TrendRadar 抓热榜
→ 生成行情
→ 生成财联社电报页
→ 生成 curated / hotlists 页面
→ 生成 /daily/ 停更占位页
→ 部署到 Cloudflare Pages
```

长内容日报已经暂时停更，所以部署耗时明显缩短。但除金十实时按钮外，其他热榜仍然不是前端实时抓取，仍依赖定时任务生成静态页面。

### 2.3 金十数据

金十数据现在不完全依赖静态页。已经加了：

```text
/api/jin10/flash?refresh=1
```

前端按钮点击后，Cloudflare Pages Worker 会在服务端实时抓金十，并按当前规则过滤：

```text
important=1 或 爆 / 沸 / 热 / 火
```

然后按时间倒序替换金十模块。

### 2.4 公众号分类网站

当前还有一个本地公众号分类网站：

```text
http://127.0.0.1:8001/
```

它现在已经有几项很重要的能力：

- 按公众号文章做赛道分类。
- 对早报、晨报、盘前必读、8点1氪、邦早报等合集标题做拆条。
- 在每个赛道内做事件聚合。
- 每个赛道输出 Top N。

它可以作为编辑供稿系统的“行业内容主干来源”，但不建议成为唯一来源。金十、财联社电报负责实时进展，微博、抖音、头条、百度等负责大众热度，公众号分类站负责赛道语义和行业内容。

当前问题是：如果排序只看已有热度或分类结果，没有批次时间窗口、progress 去重和已发送历史，就会出现较早新闻排在靠前位置的情况。

### 2.5 当前系统的主要问题

1. `/hotlists/` 是来源视角，不是编辑供稿视角。
2. 大部分来源更新依赖 2 小时一次的完整部署。
3. tab 切换不等于刷新。
4. 排序没有严格按供稿时间窗口控制。
5. 缺少“已发历史”，旧内容会反复出现。
6. 缺少 event-progress 两级去重，新进展和重复旧事实容易混在一起。
7. 公众号分类网站可以作为赛道主干来源，但不应该单独决定最终排序。

## 3. 先召回还是先聚类

结论：**先召回，再聚类，再排序。**

更准确地说，是：

```text
来源采集
→ 标准化
→ 早报 / 合集 / 长标题拆成 atomic item
→ 大召回
→ 初步分类
→ 聚类成 event
→ event 内识别 progress
→ progress 级排序
→ 每个赛道取 20 条
→ 生成可复制 Markdown
→ 记录已发送历史
```

### 3.1 为什么不是先聚类

聚类需要候选数据。没有召回，就没有候选池可以聚类。

如果一上来对所有历史数据聚类，会有几个问题：

- 数据量大，成本高。
- 很多旧新闻、低质量内容也参与聚类。
- 容易让旧的大事件持续占据靠前位置。
- 不符合“7 点、10 点、13 点、16 点这几个批次”的编辑节奏。

### 3.2 召回不是最终入选

这里的“召回”不是说直接选中，而是先把“可能有用的候选内容”捞出来。

召回应该宽一点，排序再严格一点。

可以理解为：

```text
召回：宁可多捞一点，别漏掉重要内容。
聚类：把同一件事合并。
排序：决定哪些真正给编辑看。
```

### 3.3 推荐使用两层召回

第一层是来源召回：

```text
从各来源抓取原始热榜 / 快讯 / 电报
```

第二层是编辑候选召回：

```text
在指定时间窗口内，保留可能适合选题的内容
```

完整顺序：

```text
源站内容
→ 来源召回
→ 标准化 raw_doc
→ 早报 / 合集拆成 atomic_item
→ 编辑候选召回
→ 聚类为 event
→ event 内切 progress
→ 赛道分类
→ 排序
→ 输出 Markdown
```

## 5. 标准化 / 原子化层

每个来源拿到的数据格式不同，必须先统一。这里不要只建一个 `item` 概念，建议拆成四层：

```text
raw_doc 原始文档
  ↓ 一对多
atomic_item 原子新闻点
  ↓ 多对一
event 事件
  ↓ 一对多
progress 进展
```

### 5.1 raw_doc：原始文档

`raw_doc` 表示源站里看到的一条原始内容。

例子：

- 一条微博热搜。
- 一条金十快讯。
- 一条财联社电报。
- 一篇公众号文章。
- 一篇早报 / 晨报 / 盘前必读合集。

推荐字段：

```text
raw_doc_id          原始文档 id
source_id           来源 id，例如 weibo / toutiao / jin10 / wechat
source_name         来源名称
title               原始标题
url                 原始链接
summary             原始摘要，可为空
rank                来源内排名，可为空
hot_value           热度值，可为空
source_labels       来源标签，例如 important、火、热
official_category   来源官方分类，例如金十的 A股、美股、地缘局势
published_at        内容发布时间，如果源站提供
first_seen_at       第一次抓到这个 raw_doc 的时间
last_seen_at        最近一次还看到这个 raw_doc 的时间
fetched_at          本次抓取时间
raw_payload         原始数据 JSON
```

### 5.2 atomic_item：原子新闻点

`atomic_item` 才是后续召回、分类、聚类的基本单位。

普通内容通常是：

```text
1 个 raw_doc → 1 个 atomic_item
```

但早报、合集、长标题、市场快讯可能是：

```text
1 个 raw_doc → 多个 atomic_item
```

例如：

```text
raw_doc:
【早报】美股科技股大反弹；某公司新车发布；原油大涨

atomic_item_1:
美股科技股大反弹

atomic_item_2:
某公司新车发布

atomic_item_3:
原油大涨
```

这会导致同一个原始 URL 多次出现。这个不是 bug，而是说明多个原子新闻点来自同一篇合集。

推荐字段：

```text
atomic_item_id      原子新闻点 id
raw_doc_id          所属原始文档 id
title               原子新闻标题
url                 对外输出链接，通常等于 raw_doc.url
original_url        原始文档链接
split_index         如果来自拆条，这是第几个片段
is_split_item       是否来自早报 / 合集 / 长标题拆条
split_source_title  原始合集标题
summary             原子新闻摘要，可为空
source_id           来源 id
source_name         来源名称
published_at        原始发布时间
first_seen_at       第一次看到这个 atomic_item 的时间
last_seen_at        最近一次看到这个 atomic_item 的时间
normalized_title    归一化标题
content_hash        normalized_title 的 hash
```

### 5.3 event：事件

`event` 表示同一件事。

多个来源、多个标题、多个 atomic_item 可以归到同一个 event。

```text
微博：某公司发布新车
公众号早报拆条：某公司新车发布
金十：某公司新车订单突破 X

→ 同一个 event：某公司新车发布与订单进展
```

### 5.4 progress：事件进展

`progress` 表示同一事件下的某个事实增量。

例如：

```text
event:
某公司新车发布

progress_1:
官方确认发布时间和定位

progress_2:
价格公布

progress_3:
订单突破 10 万
```

去重时不能只看 event。正确规则是：

```text
同一个 progress 发过：不再发
同一个 event 但出现新的 progress：可以再次发
```

这能避免两个问题：

- 同一旧事实换标题反复发。
- 一个事件有新进展时，因为 event 已发过而被误杀。

## 6. 召回层

召回的目标是建立一个候选池。

### 6.1 时间窗口召回

每个批次应该有自己的主时间窗口。

| 批次 | 主窗口 | 兜底窗口 | 说明 |
| --- | --- | --- | --- |
| 07:00 | 前一晚 20:00 到当天 07:00 | 过去 12 小时 | 覆盖夜间和早间突发 |
| 10:00 | 07:00 到 10:00 | 过去 6 小时 | 早盘、上午热点 |
| 13:00 | 10:00 到 13:00 | 过去 6 小时 | 午间更新 |
| 16:00 | 13:00 到 16:00 | 过去 6 小时 | 下午收盘前后 |

主窗口优先。主窗口不够 20 条时，再从兜底窗口补。

### 6.2 来源召回规则

不同来源的召回规则不同。

#### 金十数据

当前规则可以保留：

```text
important=1 或 爆 / 沸 / 热 / 火
```

排序只按时间，不按 important 或 hot 排序。important 和 hot 只作为召回条件。

#### 财联社电报

建议后续做成类似金十：

```text
按时间流抓取
保留最近窗口内内容
可按关键词或财联社标签辅助召回
```

财联社电报不应该和日报、热点脉络平行，而应该作为来源热榜或快讯源进入候选池。

#### 社交热榜

微博、抖音、今日头条、百度等可以保留：

```text
来源排名前 N
或者热度值超过阈值
或者短时间内排名上升
```

建议每个来源每次保留：

```text
Top 50 到 Top 100
```

不要过早只取 Top 10，否则很多垂直赛道会被娱乐和社会热点挤掉。

#### 行业源 / 公众号源

可以按赛道关键词召回：

```text
AI、模型、芯片、自动驾驶、低空经济、消费、跨境、电商、医药、地产、政策、金融市场等
```

这类召回可以宽一点，因为后面会聚类和排序。

### 6.3 召回不要解决排序问题

召回只回答：

```text
这条内容有没有资格进入候选池？
```

不要让召回直接决定：

```text
这条内容是不是最终第 1 名？
```

最终第几名应该由排序层决定。

## 7. 原子化 / 聚类 / 进展去重层

这一层分三步：

```text
raw_doc 原子化为 atomic_item
→ atomic_item 聚类为 event
→ event 内识别 progress
```

### 7.1 聚类输入

聚类输入应该是召回后的 `atomic_item` 候选池，而不是全量历史库，也不是原始 `raw_doc`。

原因：

- 候选池更干净。
- 更符合当前批次时间窗口。
- 计算更轻。
- 避免旧新闻持续干扰。
- 早报、合集、市场快讯需要先拆条，否则一篇文章会被误当成一个事件。

### 7.2 早报 / 合集 / 长标题拆条

公众号分类网站已经有这条规则，后续供稿系统应该继承。

命中以下情况时，先把一个 `raw_doc` 拆成多个 `atomic_item`：

- 标题像早报、晨报、午报、晚报、盘前必读、8点1氪、邦早报、钛晨报、科股快报，并且有分隔符。
- 来源像每日经济新闻、36氪、创业邦、钛媒体、虎嗅、第一财经，并且标题较长、分隔符较多。
- 标题分隔符不少于 3 个且长度不少于 48。
- 标题较长，同时包含多个市场波动词和资产词。

常见分隔符：

```text
； ; 丨 ｜ |
```

拆条后：

```text
raw_doc.url 可以重复
atomic_item.title 必须不同
atomic_item_id 必须不同
```

同一 URL 多次出现是合理的，因为多个原子新闻点可能来自同一篇早报。真正需要限制的是输出密度：

```text
同一 original_url 在同一赛道最多输出 2 条
同一 original_url 在同一批次最多输出 3 到 5 条
```

### 7.3 event 聚类

event 的目标是把同一件事合并。

例如：

```text
微博：某公司发布新车
今日头条：某公司新车售价公布
公众号早报拆条：某公司新车发布
金十：某公司新车订单突破 X
```

这些可能属于同一个 event。

event 聚类可以先用规则：

1. 标题归一化
   - 去掉标点。
   - 去掉“最新”“刚刚”“热搜”等无意义词。
   - 中英文大小写统一。
   - 去掉来源后缀。

2. URL 去重
   - 普通文章同一 URL 可以直接认为同一 raw_doc。
   - 对 `is_split_item=true` 的拆条内容，不能只按 URL 去重，要用 `original_url + normalized_title` 或 `raw_doc_id + split_index`。

3. 标题相似度
   - 归一化标题完全包含。
   - 文本相似度超过阈值。
   - 建议初始阈值：`0.78` 到 `0.85`。

4. 实体 + 动作
   - 同一公司 / 人物 / 地点。
   - 同一动作，例如发布、涨停、被调查、融资、事故、回应。

5. 时间接近
   - 同一事件通常在几小时内集中出现。
   - 时间差太远时，即使标题相似，也要谨慎合并。

推荐 event 字段：

```text
event_id
canonical_title
representative_url
atomic_items
sources
source_count
first_seen_at
last_seen_at
primary_track
secondary_tracks
status
```

### 7.4 progress 识别

progress 是 event 里的新事实节点。最终供稿应该按 progress 去重，而不是只按 event 去重。

同一 event 下可以有多个 progress：

```text
event:
某公司新车发布

progress_1:
官方确认发布时间和定位

progress_2:
价格公布

progress_3:
订单突破 10 万
```

判断是否是新 progress，可以看：

- 是否出现新动作：发布、定价、上市、回应、辟谣、调查、处罚、停牌、复牌、融资、收购。
- 是否出现新数字：价格、订单、金额、涨跌幅、伤亡数、投票结果。
- 是否出现新主体回应：公司回应、监管回应、当事人回应。
- 是否出现新阶段：传闻、确认、落地、结果、后续影响。

推荐 progress 字段：

```text
progress_id
event_id
progress_title
progress_summary
progress_type
representative_atomic_item_id
representative_url
first_seen_at
last_seen_at
novelty_score
sent_status
```

### 7.5 代表标题和链接怎么选

每个 progress 最终只输出一条标题和一个链接。

代表内容选择规则：

1. 优先选标题清楚、信息密度高的 atomic_item。
2. 优先选有明确原文链接的。
3. 优先选权威来源和快讯源。
4. 如果是新进展，优先选能体现增量事实的标题。
5. 如果是社交热榜，避免只给搜索页，除非没有更好链接。

### 7.6 群里重复的判断标准

最终不是按 URL 去重，也不是按 event 一刀切。

```text
同一 progress 已经发过：不再发
同一 event 但新 progress：可以发
同一 original_url 的不同拆条：可以发，但要限量
```

## 8. 分类 / 赛道层

### 8.1 分类可以在聚类前后各做一次

这里容易混乱。推荐做法是：

```text
item 级初步分类
→ event 聚类
→ event 级主赛道分类
→ progress 继承或微调赛道
```

item 级分类用于帮助召回和聚类。

event 级分类用于确定主赛道，progress 可以在必要时微调。例如同一个“某公司新车发布”事件，价格发布可能进汽车，股价异动可能同时影响财经。

### 8.2 为什么要 event / progress 级最终分类

同一事件可能来自多个来源，每个来源的分类都不完全可靠。

比如金十可能把一条地缘冲突新闻标成美股，因为它影响美股市场。但编辑供稿时，这条更应该进“国际 / 地缘 / 财经市场”中的某个主赛道。

所以最终分类应该基于整个 event / progress 判断，而不是只看某一条来源标签。

### 8.3 赛道建议

具体赛道可以按公众号业务来定。一个可用的初始版本：

```text
AI / 科技
财经 / 市场
公司 / 商业
消费 / 品牌
汽车 / 出行
地产 / 城市
医药 / 健康
政策 / 宏观
国际 / 地缘
社会 / 民生
文娱 / 体育
```

如果公众号分类已经有固定类目，应以公众号类目为准。

### 8.4 分类网站的角色

`http://127.0.0.1:8001/` 建议作为：

```text
人工校正分类
人工置顶 / 拉黑
维护关键词和赛道规则
查看待确认候选
```

不建议让它直接决定最终排序。

最终排序应该由供稿系统根据时间窗口、热度、来源权重、去重历史统一计算。

## 9. 排序层

排序目标是：

```text
每个赛道选出当前批次最值得编辑看的 20 条
```

### 9.1 为什么旧新闻会靠前

旧新闻靠前通常有几个原因：

1. 旧新闻在多个来源出现，累计分高。
2. 旧新闻曾经排名很高。
3. 当前排序没有强时间衰减。
4. 没有记录“上一批已经发过”。
5. 分类之后没有按批次窗口重新排序。

### 9.2 推荐排序公式

可以先用可解释的规则分数。

```text
final_score =
  freshness_score
  + heat_score
  + source_score
  + cross_source_score
  + track_match_score
  + novelty_score
  - stale_penalty
  - duplicate_penalty
  - sent_penalty
```

各项含义：

| 分数 | 含义 |
| --- | --- |
| freshness_score | 越新越高 |
| heat_score | 来源排名、热度、hot 标签 |
| source_score | 来源权重 |
| cross_source_score | 多来源同时出现加分 |
| track_match_score | 和赛道越匹配越高 |
| novelty_score | 新 progress 加分 |
| stale_penalty | 超过当前窗口扣分 |
| duplicate_penalty | 与已有 progress 重复扣分 |
| sent_penalty | 已经发过的内容扣分或直接过滤 |

### 9.3 时间衰减

强烈建议加入时间衰减。

一个简单版本：

```text
0 到 1 小时：满分
1 到 3 小时：轻微衰减
3 到 6 小时：明显衰减
6 小时以上：只作为补位
12 小时以上：默认不进普通批次
```

对不同批次可以不同：

```text
07:00 可以接受夜间 12 小时窗口
10:00、13:00、16:00 应该更强调最近 3 小时
```

### 9.4 已发送历史

必须有 sent history。

推荐维护一张表：

```text
sent_id
event_id
progress_id
title_hash
representative_url
track
batch_time
sent_at
```

每次生成前检查：

```text
同一 progress 今天发过：不再发
同一 event 今天发过但出现新 progress：可以发
相似标题今天发过且没有新事实：不再发
同一 URL 今天发过：如果是同一 progress 不再发；如果是合集拆条的不同 progress，可以发但限量
```

如果某事件有重大新进展，可以允许再次出现，但标题中必须有新的增量信息，并生成新的 `progress_id`。

### 9.5 每赛道 20 条怎么取

推荐流程：

```text
1. 每个 progress 继承或修正 event 的 primary_track。
2. 按 primary_track 分桶。
3. 每个桶内按 final_score 排序。
4. 每个赛道取前 20。
5. 如果不足 20，从兜底窗口补。
6. 仍不足 20，则保留实际数量，不要硬塞低质量旧内容。
```

## 10. 批次时间设计

### 10.1 供稿批次

| 北京时间 | 主要用途 |
| --- | --- |
| 07:00 | 早间选题，覆盖夜间、海外、早盘前 |
| 10:00 | 上午更新，覆盖开盘后、社交热榜启动 |
| 13:00 | 午间更新，覆盖上午发酵和午盘 |
| 16:00 | 下午更新，覆盖收盘、全天后续 |

### 10.2 GitHub Actions cron

GitHub Actions 的 cron 使用 UTC。

北京时间转换：

| 北京时间 | UTC |
| --- | --- |
| 07:00 | 前一天 23:00 |
| 10:00 | 当天 02:00 |
| 13:00 | 当天 05:00 |
| 16:00 | 当天 08:00 |

可以配置：

```yaml
schedule:
  - cron: "0 23,2,5,8 * * *"
```

脚本内部再按 `Asia/Shanghai` 判断当前批次名称。

## 12. 工作流拆分建议

### 12.1 当前 workflow 的问题

现在一个 workflow 同时做太多事：

```text
抓热榜
生成行情
生成电报
生成来源热榜
生成 /daily/ 停更占位页
部署
```

这导致：

- 更新慢。
- 不能高频跑。
- 任一步慢都会拖住热榜刷新。
- 不适合编辑供稿这种固定时间任务。

### 12.2 推荐拆成两个 workflow

#### workflow 1：热榜快速更新

用途：

```text
更新来源池和 /hotlists/
```

频率：

```text
每 15 到 30 分钟
```

只做：

```text
TrendRadar 抓取
金十 / 财联社快讯抓取
生成 hotlists
生成 normalized pool
部署
```

不做：

```text
日报
热点脉络
长周期分析
```

#### workflow 2：编辑供稿批次

用途：

```text
每天 07:00、10:00、13:00、16:00 生成每赛道 20 条
```

只做：

```text
读取最近候选池
必要时补抓实时源
召回
早报 / 合集拆条
聚类 event
识别 progress
分类
排序
生成 briefing Markdown
写 sent history
部署或人工复制到群
```

### 12.3 长内容日报暂时停更

长内容日报暂时停更，不再参与常规部署生成。

当前重点先放在：

```text
来源热榜
实时快讯
编辑供稿 briefing
```

等编辑供稿流程稳定后，再决定是否恢复长内容日报，或者改成每天低频生成。

## 13. 和群推送的关系

第一阶段不必直接自动发群。

可以先生成：

```text
/briefing/latest.md
```

你手动复制到群里。

`latest.md` 是第一优先产物，格式要保持简单，避免群里阅读负担：

```markdown
# 2026-07-09 13:00 编辑选题池

## AI / 科技

1. [标题](链接)
2. [标题](链接)

## 汽车 / 出行

1. [标题](链接)
2. [标题](链接)
```

不要在群版 Markdown 里输出：

- 分数
- 聚类调试信息
- 来源明细列表
- 过长摘要
- JSON 字段

这些信息可以放在 `/briefing/latest.html` 的调试视图里，但不进群。

稳定后再接：

- 飞书机器人
- 企业微信机器人
- 钉钉机器人
- 邮件
- 本地脚本复制到剪贴板

自动发群前一定要先有 sent history，否则容易重复发。

## 14. 分阶段改造计划

### 阶段 1：先做可用的编辑供稿页

目标：

```text
生成 /briefing/latest.md 和 /briefing/latest.html
```

数据来源：

- 现有 TrendRadar output
- 公众号分类结果作为主干来源
- 金十实时接口
- 财联社电报静态结果

功能：

- 按批次时间窗口召回。
- 早报 / 合集 / 长标题拆成 atomic_item。
- 聚类成 event。
- event 内识别 progress。
- 按 progress 去重和排序。
- 按赛道分类，每个 progress 归入一个主赛道。
- 每赛道输出 20 条。
- 记录已输出历史。

### 阶段 2：拆热榜快速 workflow

目标：

```text
把 /hotlists/ 更新频率从 2 小时缩短到 15 到 30 分钟
```

做法：

- 新建一个 hotlists-only workflow。
- 不跑 daily_digest。
- 不跑长周期日报。
- 只部署热榜和候选池。

### 阶段 3：财联社电报实时化

目标：

```text
财联社电报像金十一样可以前端刷新
```

做法：

- 增加 `/api/cls/telegraph`。
- 前端“刷新当前来源”支持财联社电报。
- 编辑供稿任务也可以在批次生成前实时补抓。

### 阶段 4：公众号分类系统接入

目标：

```text
分类网站成为赛道标注和人工校正后台
```

做法：

- 供稿系统把候选内容输出给分类网站。
- 分类网站写回 track override。
- 供稿系统读取 override 后再排序。

### 阶段 5：自动群推送

目标：

```text
每天 07:00、10:00、13:00、16:00 自动推送
```

前提：

- 输出质量稳定。
- sent history 稳定。
- 分类准确率可接受。
- 有人工兜底页面。

## 15. 最小可行版本

如果想尽快做出来，不要一开始做太复杂。

最小版本可以这样：

```text
输入：
  现有 output 热榜数据
  公众号分类结果
  金十实时数据
  财联社电报数据

处理：
  过去 3 到 6 小时召回
  早报 / 合集拆条
  标题相似聚成 event
  event 内识别 progress
  规则分类到赛道
  freshness + source_rank + source_weight 排序
  已发过的 progress 不再出现

输出：
  output/briefing/latest.md    群复制主产物
  output/briefing/latest.html  辅助查看页
```

这样就能先解决最痛的问题：

- 不再靠 `/hotlists/` 手动翻。
- 不再让早新闻长期排第一。
- 每个赛道都有固定格式。
- 可以直接复制到群里。

## 16. 推荐结论

你的目标不是“更好看的热榜”，而是“编辑供稿流水线”。

因此推荐路线是：

```text
来源抓取
→ 标准化 raw_doc
→ 拆成 atomic_item
→ 大召回
→ 聚类成 event
→ 识别 progress
→ 赛道分类
→ 时间窗口排序
→ 每赛道 20 条
→ 写入已发历史
→ 生成可复制 Markdown
```

先召回，再聚类；但早报、合集、长标题要在聚类前先拆成 atomic_item。

但召回要宽，排序要严。

`/hotlists/` 继续当来源看板；真正给编辑群用的，应该是新的 `/briefing/latest.md`。
